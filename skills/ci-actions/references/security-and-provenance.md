# Security and provenance

Follow repository policy; identify policy changes explicitly. The [parent](../SKILL.md) owns execution authority.

## Permissions and untrusted inputs

Grant explicit reads and only job-scoped necessary writes. A read-only `GITHUB_TOKEN` does not
constrain a separate PAT/cloud credential. Separate untrusted validation from privileged delivery.
Use checkout `persist-credentials: false` when later steps need no authenticated Git; it removes
retained Git credentials, not the runtime token or the tested code's capabilities. From checkout v6
the retained credential is a separate file under `$RUNNER_TEMP`, not an entry in `.git/config`; do
not design a step around the old location.

Event-derived titles/branches reach `run:` through quoted environment variables, never
interpolation. Validate downloaded artifact/output identity, format and paths before privileged
consumption.

Use `pull_request_target` only for its needed privileged context. Neither it nor `workflow_run` may
execute untrusted fork code alongside secrets, writes or private runner access. Upstream low privilege
does not constrain a downstream workflow. Checkout v7 refuses fork pull-request code under those two
events, and the refusal was backported to the v2 to v6 major tags, so a workflow on a floating major
tag can start failing with no workflow change. Redesign it; never set checkout's
`allow-unsafe-pr-checkout` to repair a blocked fork run. GitHub is also moving public repositories
to block `pull_request_target` by default unless an Actions event policy allows it; private and
internal repositories are unaffected. Read the applicable policy before designing on that event.

## Action and tool versions

Where a repository has adopted a workflow dependency lockfile (`.github/workflows/actions.lock`,
generated by `gh actions-lock`), it pins actions and their transitive dependencies; review its
changes. It does not pin reusable-workflow calls (`jobs.<id>.uses`), lock container images, or
follow local `./` actions, and Enterprise Server does not support it. Dependabot regenerates its
entries with version updates, and an administrator policy can require it. Without established
policy, pin reusable-workflow calls to reviewed full SHAs and `docker://` actions to manifest
digests; without a lockfile either, pin external actions to reviewed upstream full SHAs too, with
release comments and reviewable update automation.
A SHA or lockfile identifies bytes, not safety. Preserve an approved tag policy but disclose mutability; moving
refs prove neither reproducibility nor an exact release. Never replace reviewed SHAs with tags during
cleanup. Upgrades must meet runtime compatibility and organization allowlists.

## Identity and deployment controls

For a new federation-capable target, prefer short-lived OIDC after verifying issuer/audience/subject
bindings to repository/ref/environment. `id-token: write` permits token issuance, not a cloud role.
Existing target/identity policy governs: this fleet's `stack-profile` environment-secret policy remains
in force. For GCP, present Workload Identity Federation as an owner option; never create a service-account key.

Scope secrets to jobs/environments instead of broad reusable-workflow inheritance; availability does
not authorize use on another target. GitHub App installation tokens keep the `ghs_` prefix but are
now about 520 characters, not 40: never validate, mask or store one by a fixed length.

Verify plan/visibility and actual environment reviewers, branch restrictions, self-review and bypass
settings; an environment name alone is no approval gate. Missing controls need a named gap/existing
alternative, never invented enforcement or weakened protection to make YAML run.

## Verification and supply-chain evidence

Bind releases to source commit, workflow/run attempt and artifact digest. Add attestations/SBOMs when
policy or consumers need them and verify them at consumption; attestations cannot sanitize an unsafe
producer. New attestation steps use `actions/attest`; `actions/attest-build-provenance` is now only a
wrapper over it. Prepare/verify immutable-release drafts and assets before publication; recovery afterward
may require another release. The existing human process retains production readiness/execution.
