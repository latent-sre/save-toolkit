## Confirmed defects

### PIPE-01 — Google Telemetry API log ingestion is incorrectly described as Pre-GA

**Severity:** Low. **Confidence:** High. **Class:** current external-fact defect. **Evidence:** `[sourced]`, with `[verified]` local copy inventory.

**Locations:** `skills/obs-pipeline/SKILL.md:35` states that log ingestion is Pre-GA. `skills/obs-traces/references/gcp-trace.md:9` repeats that statement while explicitly naming `obs-pipeline` as its owner. Their generated mirrors have the same wording at `.github/skills/obs-pipeline/SKILL.md:35` and `.github/skills/obs-traces/references/gcp-trace.md:9`.

**Trigger → consequence:** A reader evaluates or explains the Google ingestion path using the skill's current-tense maturity claim. They receive an obsolete preview designation, potentially applying the wrong adoption/support expectations or rejecting a supported service unnecessarily. Google announced general availability of Telemetry API log ingestion on **2026-08-14**, before this audit baseline. This finding does not establish the team's project permissions, chosen route or delivery readiness. [Cloud Logging release notes](https://docs.cloud.google.com/logging/docs/release-notes).

**Important distinction:** Alloy's `otelcol.auth.google` component remains independently **public preview**. Current official docs and the v1.18.1 source registration both establish that state. Removing its `--stability.level=public-preview` requirement would be the wrong repair. [Alloy component contract](https://grafana.com/docs/alloy/latest/reference/components/otelcol/otelcol.auth.google/), [v1.18.1 registration](https://github.com/grafana/alloy/blob/v1.18.1/internal/component/otelcol/auth/google/google.go#L14).

**Smallest repair:** Correct the two canonical service-maturity statements with a dated primary source, keep the component stability flag and target-canary gates, then regenerate mirrors. The concurrent trace review cross-references PIPE-01 rather than introducing another finding.

**Verification needed:** Inspect the canonical references and regenerated copies for consistent service/component distinctions. A simple prose correction needs no cloud write or model campaign. Service GA must not change an unexercised project route from `[unverified]` to `[verified]`.

### PIPE-02 — The PowerShell stdin recipe can validate altered configuration text

**Severity:** Low. **Confidence:** High. **Class:** portability and verification-input integrity. **Evidence:** `[verified]` native transport reproduction; actual Alloy validation remains `[unverified]`.

**Locations:** `skills/obs-pipeline/references/alloy.md:150`–`:155` asks the reader to validate the exact self-contained config, then pipes `Get-Content -LiteralPath .\config.alloy -Raw` to Docker's native stdin. It does not specify the PowerShell edition or input/output encoding. `:161`–`:164` describes the resulting static-validation evidence. `docs/docker-verification.md:16` already permits a minimal read-only input mount as an alternative to stdin.

**Trigger → consequence:** A UTF-8 Alloy file contains a non-ASCII string, such as `filename = "café.txt"`, and the recipe is used in Windows PowerShell 5.1. That shell's text-to-native pipeline uses ASCII by default; implicit file decoding can also alter the characters. The child process sees a different filename from the reviewed file. Validation can therefore fail for the wrong artifact, or provide assurance about text that was never the intended input. No actual collector failure or live pipeline change was demonstrated.

**Reproduction and controls:** The caller used a disposable UTF-8 file shaped as `local.file "example" { filename = "café.txt" }`, with line breaks. A verified Python `-I -S` child only returned stdin bytes as hex. NoProfile Windows PowerShell **5.1.26100.9549** changed the filename to `caf??.txt`; adding only `Get-Content -Encoding UTF8` still produced `caf?.txt`. NoProfile PowerShell **7.6.6** preserved the UTF-8 `c3 a9` bytes in both forms. All four commands exited 0; both shells appended pipeline CRLF. Docker and Alloy were not invoked.

**Smallest repair:** Prefer a minimum read-only bind mount of the exact input file, preserving the networkless/no-credentials/no-socket boundary. Alternatively, qualify the recipe for a tested PowerShell edition and explicitly control both decoding and native output encoding. Adding `-Encoding UTF8` alone is insufficient on 5.1. Do not widen network access to compensate for an altered filename or unresolved import.

**Verification needed:** Exercise non-ASCII strings and paths through the documented transport, plus an ASCII control, and compare the received artifact before claiming exact-input validation. Then use the already approved pinned Alloy image/version when available to establish syntax/component validation separately. The native byte probe proves the transport defect without proving parser behavior.

## Recommendations, policy choices and targeted verification ideas

**PIPE-R1 — Separate naming conventions from API validity.** Low-priority recommendation; high confidence. `SKILL.md:77` calls an underscore/unit-suffixed name “not an OTel name,” and `:86` says it breaks every non-Prometheus rendering. The Metrics API grammar permits underscores; the Python v1.40.0 validator explicitly accepts them. The semantic naming guidance primarily uses SHOULD-level recommendations, including unit placement and UpDownCounter pluralization. Retain dotted names and metadata units as this team's preferred emission convention, but avoid implying universal SDK rejection or exporter breakage. The concrete trigger is an existing valid instrument with a legacy name; unnecessary renaming can split queries/history. The smallest change is wording, not bulk renaming. Verify the explanation against the API grammar and preserve the existing-instrument compatibility question. [Metrics API](https://github.com/open-telemetry/opentelemetry-specification/blob/main/specification/metrics/api.md#instrument-name-syntax), [Python validator](https://github.com/open-telemetry/opentelemetry-python/blob/v1.40.0/opentelemetry-api/src/opentelemetry/metrics/_internal/instrument.py#L44), [naming conventions](https://opentelemetry.io/docs/specs/semconv/general/naming/).

**PIPE-R2 — Attach privacy qualification to the cardinality shortcut.** Low priority; high confidence; clarity recommendation. `SKILL.md:62`–`:63` sends unbounded identities, emails, full URLs and raw SQL toward logs/traces. `otel-sdk.md:98` separately requires redaction before log serialization, Alloy `:131` requires forbidden-field filtering, and the main evidence packet also minimizes copied telemetry. Those protections mean the shortcut is not proof of an unsafe complete workflow, but cardinality suitability is not permission to retain sensitive content. Add “approved, minimized/redacted fields only” at the shortcut and preserve correlation identifiers separately from secrets or personal data. Verify an email/token-bearing URL and SQL parameters are not copied merely because the destination is a trace or log. No new redaction engine is proposed.

**PIPE-R3 — Add a small offline contract layer for the executable examples.** Low priority; high confidence; verification recommendation. Existing cases establish routing and guard posture, while the bundle contains validation/config/bootstrap instructions whose semantics are not directly checked. Prefer a few discriminating cases: one complete valid snippet versus a missing component reference, wrong `.input`/`.receiver` wiring, the Unicode stdin case, and a fan-out with one unproved branch. Keep the handoff `[unverified]` when syntax passes but delivery evidence is absent. A synthetic canary identifier belongs in evidence/log/trace correlation, not an automatically unbounded metric label. When later runtime testing is authorized, exercise per-signal rejection, partial fan-out and forbidden-field removal; do not call a collector's ready endpoint end-to-end acceptance.

Deletion-first: shorten the naming section's unsupported absolutes and repeated vendor detail before adding new material. Keep the two conditional references and retain their distinct ownership, import/network, sampling, recovery and canary boundaries. Do not duplicate all exporter defaults in tests merely to mirror prose; test the failure that a given instruction is meant to prevent.
