## Confirmed defect

### DASH-01 — The p95 dashboard fixture accepts a p50 calculation

**Severity:** Medium. **Confidence:** High. **Class:** verification false acceptance. **Evidence:** `[verified]` predicate reproduction and `[sourced]` quantile semantics.

**Locations:** `evals/build-scenarios/build-obs-dashboard-write-honours-the-carve-out.yaml:28` requests p95 latency. The panel outcome at `:127`–`:130` requires a p95 title, but checks only the presence of `histogram_quantile` and the metric name in the targets. The query check at `:142` supplies a function and metric, not the intended quantile. `evals/build_probe.py:2090`–`:2092` reads those parameters; `:2119`–`:2135` binds the query to a panel with a matching title; `:2167`–`:2176` accepts a matching queried expression with data. No condition checks the first argument is 0.95.

**Trigger → consequence:** A candidate saves a panel named “p95 checkout latency” whose expression is `histogram_quantile(0.5, sum by (le) (rate(checkout_request_duration_seconds_bucket[5m])))`, then queries that same expression successfully. The result is the median, while the displayed claim is p95. Both relevant predicates accept it, permitting materially misleading design evidence even though query identity and returned data are internally consistent. This can hide tail latency from the on-call reader. Prometheus explicitly defines `histogram_quantile` by its φ argument and documents 0.95 for p95. [Histogram guidance](https://prometheus.io/docs/practices/histograms/), [function contract](https://prometheus.io/docs/prometheus/latest/querying/functions/#histogram_quantile).

**Reproduction and controls:** The caller loaded the actual YAML panel and query predicates, supplied a three-panel model with the required datasource, seconds unit, description and “No data” presentation, and patched only `_service_request` to return that synthetic dashboard. With .95 both predicates returned TRUE. With .5 in both saved and queried expressions, both returned TRUE. With saved .5 but queried .95, the query predicate returned FALSE. The harness passed, exit 0. No Grafana/Prometheus service ran, and the complete scenario was not asserted to pass.

**Smallest repair:** Add the expected quantile to this fixture's explicit semantic contract and bind it to the actual target expression. Do not infer it from title text or a substring that could occur in a comment/label. A narrow supported-expression check can reject unsupported shapes honestly; a general PromQL parser is not automatically necessary. Preserve existing valid macro substitution and grouping behavior, while leaving the separate GRA-02/GRA-03 repairs intact.

**Verification needed:** Keep correct 0.95 as the positive case and reject 0.5/0.99 with a p95 title. Add a misleading 0.95 occurrence outside the quantile argument and ensure it cannot satisfy the check. Preserve the saved-versus-executed mismatch negative and permitted concrete-window substitution. A later behavioral run would establish whether the agent actually makes this mistake; the present finding proves only the oracle can miss it.

## Recommendations and policy choices

**DASH-R1 — Resolve the actual backend per signal instead of copying the platform shorthand.** Low-priority recommendation; high confidence. Skill `:34`–`:36` names Mimir/Loki/Tempo for OpenTelemetry-instrumented and GCP services. The frozen `stack-profile/SKILL.md:47`–`:50` itself uses that broad default, while `stack-profile/references/observability-stack.md:26`–`:30` and the metrics/logs/traces load tables include Cloud Monitoring/Logging/Trace. Thus this is not a proven contradiction with an explicit recorded-route policy at this SHA. A service whose relevant signal exists only in a native GCP backend is the useful counterexample: platform membership alone does not locate the data. Replace the parenthetical with a short instruction to load the matching stack facts and establish the service's actual signal backend/datasource. Keep the coexistence policy. Verify a mixed-backend design and an unknown-route case; the latter should remain a named information gap.

**DASH-R2 — Label the example as scrape evidence, not complete application telemetry.** Low priority; high confidence; optional precision improvement. Skill `:45`–`:48` suggests `count(up{job="<job>"} == 1) or on() vector(0)` as a telemetry-present stat and explicitly marks target applicability unverified. Prometheus defines `up` as automatically generated scrape/instance evidence. [Jobs and instances](https://prometheus.io/docs/concepts/jobs_instances/). A successful scrape can coexist with an absent application counter, and one surviving target does not establish complete population coverage. This does not make the example wrong as a scrape indicator or justify removing its useful zero-is-alarm fallback. Name that scope and, when the decision needs it, inspect the relevant metric/population's expected coverage. Verify successful scrape with missing application series, partial target loss, complete absence and valid zero traffic as separate states; do not conflate them into one green stat.

**DASH-R3 — Add one focused design-quality check before enlarging a model campaign.** Low priority; high confidence; verification recommendation. The positive discovery case at `evals/scenarios/discovery-obs-dashboard-design.yaml:3` asks for information hierarchy and missing-data behavior, but its routing check proves only selection. Skill `:54`–`:56` appropriately says to inspect representative states when available. Use a small supplied design/data fixture with one normal case, one degraded case and one missing-data case, and independently review the chosen panels, units, population, comparison window and stated limits. Include a wrong-percentile title and a missing-denominator ratio as negative examples. Start with deterministic inspectable artifacts; no additional paid/native evaluation is authorized by this recommendation.
