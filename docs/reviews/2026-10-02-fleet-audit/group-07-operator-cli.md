## Findings

### CLI-01 — EOF at confirmation becomes a traceback and operational-failure exit

**Severity:** Low. **Confidence:** High. **Class:** expected-input handling/diagnostic contract. **Evidence:** `[verified]`.

**Locations:** `skills/operator-cli/assets/cli_contract.py:167` calls `input()` without catching `EOFError`; outer handling at `:181`–`:188` and `:195`–`:206` does not cover it. `SKILL.md:31` and `:51`–`:52` define usage/missing-confirmation behavior, and `:34` reserves tracebacks for debug mode. Existing interactive tests at `assets/test_cli_contract.py:226` and interruption tests at `:299` exercise other prompt outcomes but omit EOF.

**Trigger → consequence:** The confirmation stream ends without a response. Python raises `EOFError`, so the reference exits 1 with an implementation traceback instead of declining cleanly as an unconfirmed request. No cancellation is attempted, but automation/operators receive the wrong failure category and unnecessary internals. Python documents this behavior for `input()` reaching EOF. [Exception contract](https://github.com/python/cpython/blob/main/Doc/builtins/exceptions.rst).

**Reproduction and controls:** The caller used the actual test class's command/fake client and existing simulated-TTY wrapper in an owned temporary directory. Input `y\n`: exit 0, three cancellation calls, no traceback. Input `n\n`: exit 2, zero calls, no traceback. EOF (`''`): exit 1, zero calls, `EOFError` traceback. Normal refusal and EOF both emit no JSON, so missing JSON is not raised as a unique EOF defect. An actual terminal Ctrl-D interaction was not separately tested.

**Smallest repair:** Catch `EOFError` specifically at the confirmation boundary and take the normal refusal/usage path, with a concise diagnostic if useful. Do not broaden this into catching all programming errors as service failures. Add EOF beside the existing yes/no controls, requiring no effects, no traceback and the documented refusal exit. Keep SIGINT/SIGTERM behavior distinct.

### CLI-02 — The copyable client boundary omits its definitive-rejection assumption

**Severity:** Low. **Confidence:** High for the missing precondition and demonstrated consequence; no claim about an existing production client. **Class:** contract-documentation gap. **Evidence:** `[verified]`.

**Locations:** `assets/cli_contract.py:20` lists the required client functions and `OrderError`, without defining that exception's effect guarantee. At `:129`–`:131`, every `OrderError` is classified `failed` without status readback. `SKILL.md:15`–`:16` correctly requires establishing the target API's effect contract; `:57`–`:60` warns that an error status alone does not prove no effect. The fake client's exception is bare at `assets/test_cli_contract.py:33`–`:34`; its one tested OrderError path at `:78`–`:80` rejects before mutation.

**Trigger → consequence:** A builder adapts the seam to a client whose general domain exception can also follow an applied operation. The reference labels that outcome failed even when the operation actually completed. That weakens the receipt's meaning and can mislead recovery decisions. This requires a broader exception contract than the supplied fake client's rejection path; it is not a demonstrated defect for that stub. The separate build fixture's `JobServiceError` explicitly means service rejection (`build-operator-cli-safe-requeue.yaml:52`–`:53`, oracle `:23`–`:24`) and is not classified as wrong here.

**Reproduction and controls:** The caller invoked the actual `cancel_one()` with a fake client that first recorded state `cancelled`, then raised `OrderError`: result `failed`, zero status reads. Replacing the exception with `TimeoutError` produced `succeeded` and one status read. The probe had no external or filesystem effects; it established the adaptation assumption's consequence, not real API behavior or duplicate execution.

**Smallest repair:** Document or rename the exception as a definitive no-effect rejection, and require adapters to uphold that guarantee. Where the real client cannot provide it, reconcile generic post-dispatch errors or retain UNKNOWN rather than using the rejection branch. Preserve the current valid definite-rejection case. Verify one guaranteed pre-effect rejection, an applied-then-ambiguous error, and unavailable readback; do not infer safety merely from exception naming.

## Recommendations and policy choices

**CLI-R1 — Make scaffold adoption conditional on the actual interface.** Low priority; high confidence. `SKILL.md:74`–`:77` and both asset docstrings require copying the Python command/test and retaining every case. Yet `:14` requires matching the existing language/framework, and the consuming agent at `software-engineer.md:97` says to inspect contracts before copying scaffolding. A read-only Rust status tool or a one-flag repair should not acquire a destructive-order client, confirmation prompt or unrelated lock workflow. Replace “copy both/keep every case” with preserving applicable contract cases and adapting them through the existing test runner; identify this pair as a state-changing Python example. Verify the guidance with one read-only and one non-Python task, keeping mandatory safety cases for tools that actually have those effects. This does not recommend deleting the useful reference.

**CLI-R2 — Keep lock claims within the cooperative model.** Low priority; high confidence; robustness recommendation. `cli_contract.py:67` says never remove another run's replacement file, but cleanup does a pathname ownership check and subsequent `unlink()` separately at `:92`–`:93`. A replacement between those operations is outside what the check can atomically prove. Existing tests replace the file before cleanup and correctly preserve it. Because the skill explicitly scopes the lock as cooperative and local (`SKILL.md:85`–`:86`), this review does not claim overlapping well-behaved invocations or a filesystem-adversary guarantee was disproved. Clarify those assumptions and consider a controlled replacement-between-check-and-unlink negative if stronger protection is required. Do not introduce distributed locking absent a target requirement.

**CLI-R3 — Say what the reference receipt and resume behavior do not implement.** Low priority; high confidence; contract-scope recommendation. `SKILL.md:60`–`:62` asks for target, item, operation ID, outcome, UTC time and actor, with resume skipping successes and reconciling UNKNOWN. The reference emits only an `items` object containing `id/status` (`cli_contract.py:139`–`:144`) and a later run simply reselects stale orders; it does not load a persistent operation journal. This is a useful minimal fixture, but not proof of the full metadata/resume requirement. State the boundary and require the adapter to choose the appropriate receipt persistence/idempotency contract. Verify a restart after an ambiguous effect and delayed visibility when a real target needs that protection. Avoid adding a generic durable-journal subsystem to every CLI.

Additional verification priority: preserve the strong existing oracle mutations and add the narrow EOF/adaptation cases before spending on larger native campaigns. Real TTY behavior, externally delivered termination, blocked network calls, receipt durability and API idempotency require tests at those actual boundaries. A fake client's `signal.raise_signal` proves the handler path, not every CI cancellation mechanism or uninterruptible call. Bounds on external calls belong in the adapted client; the reference interface has no network implementation.
