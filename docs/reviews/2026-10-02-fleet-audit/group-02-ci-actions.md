## Confirmed defect

### CI-01 — Artifact-promotion oracle accepts deployment of unrelated bytes

**Medium severity; high confidence; [verified] deterministic in-memory reproduction.** Location: `evals/oracles/pcf-deploy-job/probe_ci_workflow.py:292-299`; invoked by `evals/build-scenarios/build-software-engineer-adds-pcf-deploy-job.yaml:234-237`.

The skill requires promotion of the tested artifact with source/run identity (`SKILL.md:79-82`; `execution-and-runners.md:76-80`). The build fixture produces `checkout-build`, and its evaluator advertises an artifact-promotion result. However, `_artifact_promoted` only rejects a run step mentioning `build.sh` and looks for a download step with the expected artifact name. It never connects that download to the path passed to `cf push`.

**Concrete trigger → consequence:** an authored job downloads `checkout-build` into `reviewed-artifact` and then runs `cf push checkout -p /tmp/unrelated-bytes`. The named predicate returns success, although its result establishes only that a download step exists. Candidate verification can therefore credit promotion of tested bytes without proving which bytes would be deployed. This is an evaluator defect; it does not show that any live workflow deployed the wrong artifact.

Root reproduced the predicate with Python 3.14.7, exit 0, using a synthetic job dictionary and no shell or CF execution. `_artifact_promoted` returned `None` (accepted). Removing the download was a rejecting negative control. The separate authentication and targeting predicates also accepted the supplied dictionary; their narrower implications are documented in CI-R1. No claim is made that this synthetic dictionary passed every scenario assertion or actionlint.

**Smallest correction:** for this deliberately bounded fixture, verify that the deployment path resolves to the downloaded `checkout-build` payload and required reviewed manifest. Reject unrelated or unresolved paths rather than treating an artifact download as sufficient evidence. An alternative is to rename the current assertion to its narrow meaning and add one focused promotion check; simply weakening the skill's promotion requirement would lose the intended guarantee.

**Verification needed:** a positive fixture using the downloaded payload; negatives for a different `-p` file, a download ignored by the push, and an intervening replacement/rebuild. Prefer a safe fixture command recorder or a bounded declarative path check to a general-purpose shell parser. Keep the current static test for the bundled example (`scripts/test_skill_assets.py:106-132`), which already checks its download/push path binding; the missing protection concerns arbitrary jobs produced by the build trial.

## Recommendations and verification gaps

### CI-R1 — State and test the authentication prerequisite explicitly

**Priority: medium; recommendation/coverage gap; [verified] observed acceptance, [unverified] operational outcome.** Location: `probe_ci_workflow.py:302-330`; scenario assertion at `build-software-engineer-adds-pcf-deploy-job.yaml:238-245`.

Root's synthetic job omitted `cf auth` entirely yet `_cf_auth` and `_cf_target` both returned success when `cf api` and `cf target` preceded `cf push`. The positional-credential negative control was rejected. The oracle validates any auth command it sees but does not require one or establish a pre-existing authenticated session. On a clean runner the job could fail; on a persistent runner it could reuse an unintended session. Neither operational outcome was executed.

This is kept separate from the confirmed defect because the current oracle's written predicate quantifies “every cf auth” rather than explicitly requiring an auth operation, and a different validated authentication path can be legitimate. The fixture supplies environment credentials but does not establish a prior session. Clarify that prerequisite in the fixture, then add absence and out-of-order negatives for the selected authentication design. The bundled planning example already calls `cf auth` inside a new private CF_HOME (`pcf-deploy-job.md:86-95`); do not rewrite that example to compensate for the evaluator's gap.

### CI-R2 — Preserve the difference between shape checks and operational assurance

**Priority: medium; coverage recommendation; [verified] static coverage limits.** The build oracle detects lexical command shape. Its runner check requires labels but no approved group (`probe_ci_workflow.py:163-175`); its rollback check accepts a command anywhere in the workflow or a rollback-named job with run steps (`:347-358`). There is no health, manifest identity, digest binding, first-deploy recovery, or authentication-home assertion in its fifteen-case catalog (`:379-395`). The more complete bundled example has independent tests; those do not validate every model-authored result.

The fixture supplies only runner labels and deliberately uses repository-owned major-tag policy, so do not silently impose undisclosed group names or SHA policy on that trial. First narrow the advertised evidence to the exercised contract. If stronger readiness claims are needed, supply the missing approved facts and add only the necessary discriminating cases. Remove or relocate the historical “15/15” and “thirty-two files” claims from the live scenario comment (`build-software-engineer-adds-pcf-deploy-job.yaml:192-196`) unless a current decision depends on retained, inspectable evidence. A historical count is not fresh negative coverage.

The optimization and bounded-validation exact-JSON scenarios are useful calibration/regression questions. They do not prove that a model actually inspects downstream workflow code, honors a host denial, or reconciles an uncertain submission. Future behavioral acceptance should choose a bounded budget and harmless fixture interaction; this audit does not authorize a new campaign.

### CI-R3 — Make two small wording changes before considering restructuring

**Priority: low; readability recommendation.** In `pcf-deploy-job.md:38`, replace “a human starts each deploy” with “explicit dispatch from main.” The YAML predicate constrains the event and ref; workflow_dispatch is also callable through CLI/API, so that predicate alone does not identify a human. The existing environment and exact-approval preconditions should remain. [sourced] GitHub documents UI, CLI, and REST entry paths.

Add a short Contents list to the 205-line PCF reference, consistent with `agent-authoring/references/claude-code-frontmatter.md:83`. Delete repeated explanation before adding more instructions. Keep the illustrative YAML and the test extraction connected; extracting a new script solely to shorten Markdown adds another mechanism and is not justified by this review.
