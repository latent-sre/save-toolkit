**Material finding: unsupported timeout and slot-hold bound (high confidence).** The fixed
assessment patches in `fix-sonnet/run-{1,2,3}/outputs/workspace.patch` state a 36-second bound at
lines 28/30, 23/30/39 and 29/34 respectively. Run 3 says, "That is a maximum; the actual hold
time is unknown." The supplied seven-line handler passes `timeout_seconds=12` to an unseen
`ledger.post` implementation. It establishes at most three calls when earlier calls return falsy,
an early return on success, and an uncaught exception path. It does not establish timeout
enforcement, exception-versus-false return behavior, cancellation, call overhead or slot release.
Calling 36 seconds a proven elapsed-time maximum is unsupported, even when a later paragraph
acknowledges that cancellation is unknown.

[verified] The original three assessments also make the timeout assumption, so this evidence
does not attribute the defect to the skill-loading repair. The oracle deliberately checks
section presence and the JSON decision, leaving soundness of the prose to review. Its PASS is
consistent with that narrower contract and must remain visible beside this finding.

Correction direction: retain the supported maximum call count; describe 36 seconds only as a
conditional nominal sum; require evidence of timeout/exception/cancellation behavior before
claiming an elapsed-time or occupancy bound. Specify admission before acquiring a shared slot,
or nonblocking rejection/separate scheduling, for a proposed concurrency limit. Waiting for a
semaphore while already occupying the shared pool can still starve reads. The original run 3
states that placement requirement explicitly; the fixed designs leave it insufficiently explicit.
Do not infer missing customer roles: fixed runs 1 and 2 introduce trading-account users that
the fixture never names.
